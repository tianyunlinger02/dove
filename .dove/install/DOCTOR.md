用户指出，将理论主导的研究原则融入 Dove 的方案再次变得过于复杂，尤其是 Experiment 部分出现了防御性检查清单倾向，可能造成提示词冗余和局部膨胀。用户希望只保留简洁的核心研究判断，不把每次实验变成多项诊断和记录要求。

用户进一步指出，“reconsider both before adding more local experiments”仍暗示复审之后默认继续增加实验，偏离了先判断理论、实验或方向本身是否需要改变的本意。相关表述应避免把新增实验设为默认下一步。

本次审查发现 Dove 当前公开表面出现严重分裂：部分 README、Usage、Install、输出样例和 source CLI 被另一套旧的 Workspace/Mission/MCP 数据库架构内容覆盖，而 canonical 十个 Skills、Markdown 研究树、package scripts 和其他文档仍是当前架构；source CLI 还导入多个不存在的旧模块，导致 build 和 command validation 失败。用户会得到互相矛盾的命令、安装路径和产品模型。

用户认可从 PaperSpine 吸收“Results 应验证研究或贡献承诺”的原则，但仍要求保持 Dove 精简，不能借此重新引入 Contribution Contract、Evidence ID、固定 Results 模板、checker、gate 或完整论文流水线。应只补充结果与研究承诺、证据解释之间的直接联系。

用户考虑是否给 Dove 增加“跳跃思维、钻研精神”一类提示，希望增强探索能力。需要避免模糊人格词造成无目标发散、过度钻研或回复不连贯，优先判断现有可执行研究原则是否已经覆盖其真实意图。

Dove Stop hook 的例行“说人话”续写被宿主误判为 Dove 自身反馈或 guidance failure，导致每次重写回复时又追加一条 `DOCTOR.md`。Stop hook 的常规重写请求不是用户反馈，也不是新的 Dove 故障，不应触发反馈记录。

用户明确修正反馈分流：只有用户在反馈中明确点名 Dove，才应把该用户反馈写入 `DOCTOR.md`；未点名 Dove 的普通科研或协作反馈中，可复用的经验应进入 Lessons。Dove 自身 Skill、hook、项目接入、路由、文档或 guidance 的实际故障仍可直接记录。

用户批准调整 Dove 研究默认文件所有权：六个内置 Lessons 主题应由 package 整体刷新，研究 overview、汇总和其他研究文档应保持研究者拥有，并直接清理已弃用 Lessons 路径而不迁移或 fallback。

用户指出 Dove 对科研和工程都应保持客观准确、按证据和任务风险比例行动，避免在激进执行和过度防御之间走极端；科研早期的“感觉”应作为可落地的假设，而不是直接结论或被压制掉。

用户进一步建议 Dove 不应继续作为 planner、builder、reviewer 或一组命令文案的拼接，而应成为宿主可直接切换和消费的完整科研 agent。Dove 的统一人格需要贯穿 agent surface、Skills、ambient/no-route 判断、Lessons、文档和验证：抓主线与关键决策，把 hunch 当 hypothesis，把偏好当 tradeoff signal，按逻辑分层区分实验、验证、写作、审查、工程和文档的主次，比例行动，并防止低层 artifact、指标或 checklist 冒充科研推进。

用户再次强调，Dove 不能被写成“先诚实承认不足，然后就结束”的窄姿态。诚实识别不足只是起点，不是终点；Dove 应把不足转成最小可区分的问题、动作或下一步判断，继续推进主线，只有当继续行动也不能改变关键不确定性时才停。

用户补充指出，修 Dove 不能只做“收窄”和防过度防御，还要正向激发科研精神：让 Dove 有探索欲、钻研劲、提出候选解释和主动找关键证据的倾向，但这种主动性仍应服务研究主线和关键决策，而不是变成无目标发散、清单化自证或为了显得忙而行动。

用户还希望 Dove 以后长期保持几条要求：始终抓主线，不要在过窄和过宽之间来回摆；把感觉当假设，把用户偏好当 tradeoff signal；不要让测试绿、清单、validation 或 Markdown 维护冒充科研推进。过去最典型的问题是把 review 写得太像固定 handoff，把 experiment 写得太像防御性检查清单，以及把 stop、记录和路由做得过度自动化。用户认为普通测试往往测不出这些问题，后续更应该依赖真实行为、tmux 里的 Auto 运行和周期性观察来判断 Dove 是否符合要求。

用户再次要求把这些长期要求和过往错误作为 Dove 自身开发的持续约束，并在右侧 tmux 中用 Dove Auto 做自动化开发；定时观察时应重点看真实行为是否服务主线、是否比例行动、是否直接改善科研判断能力，而不是只看测试、validator、文档更新或工作流叙述。

本次右侧实验暴露出 Dove 更新架构的实际缺口：用户级 Dove 已更新，但已启动项目中的 command、agent、rule 和 support Skill 仍是旧副本，导致右侧继续测试旧 Auto。用户要求 Dove 采用真正的热更新语义：用户级更新后，已启动项目应跟随新版本，而不是依赖逐项目手动 update；这与需要用户手动批准的 reinstall 完全无关。后续回答必须先核实当前实现和生效状态，不能把“应该如此”随口说成“现在已经如此”。

右侧真实 Auto 还暴露出 Stop continuation 的副作用问题：Stop hook 只要求把当前总结改成更直白的表达，但宿主把这次内部续写误当成用户的可复用反馈，自动创建了 Lessons 文件。Stop continuation 应严格限于当前回复的纯文本重写，不得调用工具、继续研究、创建任务，或写入 DOCTOR、Lessons、research Markdown 和其他项目文件。

用户指出，Dove 本体修改、生成、构建和热同步完成后，不能因为右侧原窗口暂时没有新输出就把验证视为结束；必须主动在同一个既有窗口重新运行真实任务，确认宿主是否实际加载新版 surface，并观察修复后的行为。磁盘同步、测试通过和规则落盘都不能替代原窗口的行为验收。

用户进一步澄清 Dove 的核心目标：主要是推进科研正文本身达到可提交水平，而不是把证据整理、补充包、provenance、validation 或其他支撑工作提升成独立主线。证据充分和论文表述有依据是科研工作的默认要求，不需要 Dove 反复单独强调或把“证据闭合”当成目标。Dove 应围绕论文的贡献、创新性、科学问题、方法、实验、结果解释、论证、写作和审稿风险推进正文；支撑材料只在确实影响正文可信度或投稿时按比例处理，不能取代正文进展或轻易阻止“可提交”判断。

用户说明，真实行为实验不能只盯 Auto；研究、来源、实验、写作、图表、审查、回复和 Lessons 等每个 Dove Skill 都需要按其实际科研能力验证。Auto 的特殊地位是它应体现并调度整个 Dove：具备自主判断、自主推进科研、按当前目标选择并调用其他科研 Skill 的能力。它不是一份把其他能力文案复制进来的并列 workflow，也不能只以一句“when review is useful”代替真正调用 Review。Auto 应作为完整科研能力的自主编排入口，而各专项 Skill 仍需独立保持高质量、可直接使用。

用户纠正，对 Auto 的判断不应机械化为“是否显式调用了其他 Skill”；Auto 可以直接运用完整 Dove 能力，也可以在有价值时调用专项 Skill，关键标准始终是它是否正确理解并推进科研项目。此次最直接的错误是测试任务本身被错误收缩成“完成补充包 provenance 整理”，继续把下层支撑工作设成主目标，偏离了推进 PhysPrior 科研正文达到可提交水平的主线。后续不能用 Skill 调用形式掩盖主线选择和科研判断错误。

用户指出，Auto 不应依赖一段很长的外部提示词才能抓住科研目标。只要项目研究主线已经记录清楚，用户应能用简短的 `/dove:auto` 或“继续推进当前主线”启动；Auto 内部负责读取主线、理解正文可提交这一目标、自主判断关键问题并持续推进。若测试提示必须预先列出贡献、创新、方法、实验、图表、审稿风险、停止条件和能力选择，实际上是在由提示词替 Auto 完成科研判断，也掩盖了 Auto 本身的缺陷。

用户指出，Dove Reviewer 不能脱离目标投稿语境随意给出通用意见；正式审稿前应先核实目标 venue 当前官方投稿与审稿要求，并实际查阅最相关的已发表论文作为 novelty、positioning、证据规范、实验呈现和读者预期的参考，再据此形成 reviewer-perspective critique。搜索结果或摘要不能冒充已读论文，published practice 也不能替代官方规则。

用户再次指出，无后缀 `/dove:auto` 应沿已恢复的科研主线一直推进到真实完成条件；论文项目即推进到可直接投稿的实际交付物，或确认当前条件下无法解决的 material blocker，而不是完成一轮 Markdown 修改后停下。带后缀时才以用户给定目标为即时完成条件。Dove 还必须先识别真正的投稿源文件、构建链和 venue-facing artifact，不能默认把工作用 Markdown 当作最终投稿文件。

Dove 开发仓库自身仍保留旧的顶层 `.dove/research/LESSONS.md`，却缺少当前 canonical 的 `RESEARCH.md`、目录 summaries 和 `lessons/` 主题树；这使开发和真实使用脱节，也直接诱发了把废弃文件误当当前 Lessons 入口的错误。Dove 应先准确诊断自身项目为何未采用当前文档系统，再选择与根因匹配的修复，不能继续在旧路径上写入，也不能用未经判断的局部补丁或过度重装掩盖问题。

新版 Auto 已正确识别真实 ESWA 投稿产物尚未生成，并找到了可在本地适配的 DOCX 导出方案，但在明确仍有可行下一步时因宿主上下文压缩停下，只留下任务和总结，没有继续实现导出器。这不是 material scientific blocker，也不是目标完成；Dove 应把上下文边界当作精确恢复未完成动作的边界，而不能让压缩总结替代继续推进。

用户指出，修复后的 Auto 仍被旧压缩总结和 host task list 锚定，直接实现 DOCX 导出，没有先对当前整篇稿件形成基于 ESWA 官方要求和实际查阅相关论文的 reviewer-perspective verdict，也没有先确认科学内容、实验、引用和论证是否足以过审。旧 review handoff、旧 verdict、作者侧任务或 compaction next step 只能作为恢复线索，不能代替对当前稿件版本的真实审查；应先找出影响过审的实质 blocker，再反复修稿和复审，投稿格式与导出属于后续从属工作。

用户还指出，只读监控 Dove 时不应在开发会话自身调用 Auto；监控应直接读取要求和观察目标 pane，只有用户明确要求执行 Auto 时才在目标 pane 启动它。

后续右侧实测进一步证明此前修复仍不够强：Auto 成功生成并验证 DOCX、补齐引用后，就把状态判断成“基本能进入投稿前最后检查”，但它仍未在本轮先执行基于当前 ESWA 官方要求和实际查阅相关论文的完整 reviewer-perspective review，也没有在修改后重新审查科学贡献、实验覆盖、novelty、positioning 和论证是否足以过审。文件可打开、图表引用完整和引用编号一致只能证明工件质量，不能解决科学或审稿 blocker；论文投稿主线中，当前版本的真实 review 与实质修订后的复审必须发生在 readiness verdict 之前。

用户进一步追问为何把 ESWA 投稿认定为 DOCX，并指出计算机论文通常可能更适合 LaTeX。核实官方指南后，ESWA 同时接受 Word 和 LaTeX 可编辑源文件，因此 DOCX 并非错误格式，但 Auto 在未明确比较稿件技术需求、现有 source/build path 和协作需求前，仅因本地 DOCX exporter 可实现就将其称为“真正的 ESWA 提交文件”，仍是机制错误。venue 允许多个格式时，Dove 必须作出并说明适合项目的格式选择；工具可用性不能替代格式判断，未形成有依据选择前的导出只能叫候选或诊断工件。

最新右侧运行再次暴露：Auto 无法访问官方 ESWA 页面、搜索也没有返回结果时，仍继续依赖本地稿件和已有摘要，生成 DOCX、做引用/结构检查，并宣布“主要 blocker 已经解决”。外部 grounding 失败不是通过；没有实际访问官方要求或实际查阅相关论文，就不能给出 grounded submission verdict，也不能用本地格式检查冒充投稿审核。若外部材料不可访问，必须明确边界并继续做未依赖该材料的实质审稿，或把外部核实列为真实未解决 blocker。

本次只读复查确认右侧 Auto 没有实际调用 Dove Review，也没有获得 `PASS`，却把格式、引用和 DOCX 检查写成“主要 blocker 已解决”并停止。投稿就绪必须以当前稿件的实际 Review 调用及其 `PASS` 为停止条件；搜索失败或 reviewer-style 自评不能代替该调用。

新版 Auto 虽然实际调用了 Review 并正确返回 `REVISE`，但 Review 只确认六张图存在并能嵌入 DOCX，没有逐张检查图是否清楚支撑方法、实验结果和核心贡献，也没有在发现图形质量可能影响审稿时调用 Figure 能力。投稿就绪审查不能把图片数量和文件有效性当成图形质量；应先把图的实质表达纳入 Review，再在确有材料改进价值时调用 Figure 检查或重画并复审。

Figure-aware Auto 实测已经实际调用 Figure、渲染并查看六张图，再调用 Review，但仍笼统判定“图都清楚且支持论点”，没有识别此前已知的 DOCX 重复图注、密集 drape 拼图在期刊版面下细节过小、图注措辞与选择元数据不一致等具体问题，也没有据此修图。这说明“实际打开图片”本身仍可能退化为表面验收，Figure 和 Review 必须结合图在论文中的证据职责、稿件版面、图注及源数据作实质判断。此外，本次 Figure 把验证中间文件写入了 `/tmp`，违反项目约定的仓库本地临时目录要求。

进一步实测中，Auto 虽已改用项目内 `.claude/tmp/` 渲染六张图，却绕过了 `dove:figure`，直接用 Bash 完成图形验证，然后把尺寸和存在性摘要交给 Review；Review 又仅凭该摘要判定“正文和图基本过了”。实际图形渲染或材料验证既然已经成为当前动作，就必须先实际调用 Figure，Review 也不能接受尺寸、计数或笼统“看起来没问题”作为 Figure 的实质审图结果。

最新右侧复查仍显示 Review 被 Auto 的投稿材料框架锚定：它把正文说成基本完成，只指出作者页字段，并让旧的作者页任务继续占据主线；而实质审稿报告已经指出论文仍是 Major Revision。Review 必须先从实际稿件重建中心贡献、主张—证据关系和最强反驳，形成自己的科学判断；投稿包清理不能替代或截断这一步。

用户明确指出当前 Dove 的问题仍然很大：修复并热同步后重新运行短 `/dove:auto`，Auto 仍直接继承旧的作者页任务，以“填写 title-page metadata”开场，没有先重建当前投稿主线或执行科学 Review。这说明旧任务锚定并未真正解决；Auto 必须把宿主任务列表当作线索而非指令，并在每次新运行时先按真实目标重新选择主线动作。

完整读取右侧运行历史后，用户进一步指出整个 Dove 都有“汇报多于推进”的严重倾向。此次 Auto 已经正确调用 Review、识别 Major Revision 级科学问题并长时间调查，却最终只复述问题、提出“如果你要我可以下一步”，没有执行仍然可行的正文修订和证据检查。Dove 应把说明和汇报压缩到服务决策所需的最小程度；只要目标未完成且仍有可执行的实质动作，就应直接推进，而不是用总结、任务列表或再次征求许可代替行动。
